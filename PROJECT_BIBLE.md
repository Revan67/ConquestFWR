### Staged retail-restoration governance (methodology decision, 2026-10-15)

M2.5 answered the *method-selection* question, not the whole executable/source mapping question. The default unresolved-correspondence workflow is **deterministic extraction → retail subsystem/domain identification → small independently justified candidate family → guided decompilation → retail behavior/data/ABI comparison → independent review → parent adjudication**. Use only the evidence needed for the local risk. Historical source, archive packages/mods, compatibility projects and documentation are secondary leads, never sole retail behavior authority. Body/IR and V4 rankings may generate candidates, but their numerical score alone cannot establish identity or block a locally evidenced repair. Do not hard-prune migrated functions or use reviewed development identities as same-run matcher seeds. Preserve the existing 0/45 V4 transfer failure and all negative captures; suspend universal tuning rather than relabeling V4 obsolete or failed in every use.

**Correspondence classes (separate from project finding status and evidence character):** `CORRESPONDENCE_VERIFIED` requires strong independent retail/source role or identity evidence sufficient for the proposed implementation boundary; `CORRESPONDENCE_STRONG_CANDIDATE` favors one identity but retains a material uncertainty, permitting only tightly bounded experiments; `CORRESPONDENCE_EQUIVALENCE_SET` retains all plausible siblings; `CORRESPONDENCE_GUIDED_ONLY` supports local functional understanding without reusable identity; `CORRESPONDENCE_OPEN` is insufficient. Do not choose an equivalence-set member for convenience. A behavior/layout repair can pass local gates without proving exact function identity if the retail target, current divergent path and acceptance test are independently established; preserve candidate identity status after such a repair.

**Subsystem-local readiness gates:** A — state the exact retail behavior/layout/ABI/value/control flow; B — identify authoritative retail evidence separately from supporting source/history; C — demonstrate the current code or runtime divergence; D — bound affected files/functions and ABI, parser/data, save, renderer, network and mission-DLL impacts; E — specify an observable or deterministic acceptance/rejection test before coding; F — resolve contradictory evidence *inside* that boundary. OPEN questions elsewhere do not block a local stage. A stage may be `READY_FOR_IMPLEMENTATION` only after all six gates are reviewed. Stage statuses are `RESEARCH_ONLY`, `READY_FOR_IMPLEMENTATION`, `IMPLEMENTING`, `VALIDATION_PENDING`, `VALIDATED`, `REJECTED_OR_REVERTED`, and `BLOCKED`. Subsystems may occupy different statuses concurrently: bounded research → ready → implementation → validation → next target. Compilation, a matching resource byte, and observed gameplay acceptance prove different things; promote only the result actually tested.
