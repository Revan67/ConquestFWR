# Retail Conformance Audit — 2026-08-20

Scope: mission scripting ABI (deep), plus a sweep of code unaudited by the 2026-05-18 pass.
Baseline for source drift: `a9872e3` (initial VS6 source push).
Binary ground truth: retail `mission.dll` (548,864 B, Oct 2012) and the 18 retail script DLLs.

---

## 1. Mission scripting ABI — CLEAN ✅

The retail mission scripts (`script01`–`script16`, `Mantis_T`, `Sol_T`, all Oct 2012) are
prebuilt binaries we cannot recompile. They bind to our `Mission.dll` by **decorated C++
export name**, so any signature, calling-convention, or type drift is a hard runtime failure.

Verified by three-way symbol set arithmetic (`dumpbin /exports` + `/imports`):

| Module scripts bind to | Symbols demanded | Unsatisfied |
|---|---|---|
| `Mission.dll` | 153 | **0** |
| `Trim.dll` | 2 | **0** |
| `DACOM.dll` | 2 | n/a (retail DLL, unmodified) |
| `KERNEL32.dll` | 62 | n/a |

**All 155 symbols resolve exactly.** Because the MSVC mangling encodes calling convention
(`SA` = `__cdecl`, `SG` = `__stdcall`), this also proves convention alignment — e.g.
`?PlayMusic@MScript@@SGXPBD@Z` is `__stdcall` in both retail and our build.

Conclusion: the script binding layer is not the source of the DACOM crash.

### 1a. Latent drift — `wchar_t` mangling (4 symbols)

VS6 typedef'd `wchar_t` as `unsigned short` (mangles `G`); VS2022 treats it as a native type
(mangles `_W`). Only `StringTable.vcxproj` sets `TreatWChar_tAsBuiltInType`; `Mission.vcxproj`
takes the VS2022 default. Result — these four exist in retail but not in ours under the retail name:

| Retail | Ours |
|---|---|
| `?GetCountedString@MScript@@SAPAGK@Z` | `...SAPA_WK@Z` |
| `?GetPlayerNameBySlot@MGlobals@@SAKKPAGK@Z` | `...SAKKPA_WK@Z` |
| `?GetPlayerNameFromDPID@MGlobals@@SAKKPAGK@Z` | `...SAKKPA_WK@Z` |
| `?SetupComputerCharacter@MGlobals@@SAXKPBG@Z` | `...SAXKPB_W@Z` |

**Latent, not active** — no retail script imports any of them; the only callers are
`Conquest.exe`/`Trim.dll`, which we rebuild consistently. Fixable with `/Zc:wchar_t-` on
Mission.vcxproj if exact retail parity is wanted. Not urgent.

### 1b. 28 exports we have that retail does not

`EnableSpecialAttackCap`, `EnableSpecialEOACap`, `GiveCommandKit`, `OrderAttackPosition`,
`SetRallyPoint`, `TeraformPlanet`, `SetSpectatorMode`, `StartFlashUI`/`StopFlashUI`,
`PlayFullScreenVideo`, `GetFormationName`, `GetJumpgateWormhole`, `SelectUnit`, `SetReady`,
`EndMissionSplash`, `IsPartValid`, the `ScriptParameterList` class, etc.

`MScript.h` has **zero drift from `a9872e3`** — these were already in the source release.
They are sequel (CQ2) API surface, consistent with `project-source-origin`. Extra exports are
harmless to retail scripts. Removing them is cosmetic conformance work, not a correctness fix.

## 2. Script-boundary struct layouts — GAP ⚠️

Matching symbol names prove nothing about struct layout: `OrderTeleportTo(const MPartRef&,
const MPartRef&)` mangles identically whether `MPartRef` is 16 or 20 bytes. Nine types cross
the boundary:

| Type | Used by N imported fns | static_assert? |
|---|---|---|
| `MPartRef` | 82 | **none** |
| `UNIT_STANCE` (enum) | 3 | **none** — see note |
| `MGroupRef` | 3 | **none** |
| `TECHNODE` | 3 | **none** |
| `CQBRIEFINGITEM` | 2 | **none** |
| `CQSCRIPTDATADESC` | 1 | **none** |
| `AIPersonality` | 1 | **none** |
| `MISSION_SAVELOAD` | 1 | **none** |
| `CQSCRIPTENTRY` | 1 | **none** |

**Not one has a compile-time size assertion**, despite this being the project's established
pattern elsewhere (`project-spaceship-binary-layout`). `sizeof(MPartRef)=16` is recorded in
memory only as a *runtime* observation.

`MPartRef` inspected and confirmed correct: 4 × `U32` = 16 bytes, no vtable. The `#else`
branch in `MPartRef.h` is the `_ADB` schema-compiler view, not a second runtime layout.

**Note on `UNIT_STANCE`** — the only enum in the set, passed *by value* in three script-called
functions. Inspected (`DMissionEnum.h:262`): plain 4-value enum, no explicit underlying type,
no bitfield use, so both VS6 and VS2022 give it `int` (4 bytes). Low risk — but this tree has
a documented history of VS6/VS2022 enum sizing breaking layout (`836a0c2`), so assert it anyway.

**Recommendation:** add `static_assert` for all nine. This is the exact failure mode that
produces a deferred AV with a float read as a vtable — silent, and invisible to symbol checks.

## 3. Suspicious guard in `MGlobals::initMissionData` 🔴

```cpp
// Guard: non-mission archetypes (lights, nebulae) don't have MISSION_DATA_BIN
// at offset +44, so pInitData reads garbage. Race out of range signals bad pInitData;
// bail before the out-of-bounds playerTechLevel access.
if ((unsigned)part->race > (unsigned)M_VYRIUM)
    return;
```

**The guard's stated premise is factually wrong.** It claims non-mission archetypes such as
nebulae lack `MISSION_DATA_BIN` — but `BT_NEBULA_DATA` demonstrably *has* it
(`DInclude/DNebula.h:97`), as do `BT_BLACKHOLE_DATA`, `BT_JUMPGATE_DATA`, `BT_MINEFIELD_DATA`,
`BT_PLATFORM_DATA` and others. So whatever makes `pInitData` read garbage, it is **not** "the
struct doesn't have a missionData member."

Checked and *not* the explanation: `MISSION_DATA_BIN` is 40 bytes and `MISSION_DATA` is 72,
both locked by `static_assert` in `DBaseData.h:295/318`. Memory's "`MISSION_DATA` 72B at +104"
refers to its offset inside `BT_PLANET_DATA`; the guard's "+44" is a different archetype's
offset. Those do not conflict.

That leaves the likely real cause as **type dispatch** — some object reaching `initMissionData`
whose archetype is not the type the code assumes, so `pInitData` points at a correctly-sized
struct of the *wrong* archetype. The guard hides that mismatch instead of reporting it.

Directly relevant to the open DACOM investigation: a `pInit` pointing into the wrong archetype
is exactly how a float world coordinate (`0x46800000` = `16384.0f`) ends up where a pointer is
expected. **Worth investigating ahead of more `GetSectorEffects` breadcrumbs** — replace the
silent `return` with a log of the offending archetype name and `mObjClass`, and the mismatch
identifies itself.

Retail also assigned `playerID = 0` when `race == M_NO_RACE`; our version dropped that
assignment (deliberately, in `506d8db`). Validated at the time, but it is a live divergence
from retail semantics worth keeping in mind.

## 3a. Assertions downgraded to silent returns

`MGlobals` converted several `CQASSERT`/`CQASSERT2` into silent early-returns:

```cpp
- CQASSERT2(playerID1-1 < MAX_PLAYERS && playerID2-1 < MAX_PLAYERS, ...);
+ if (playerID1 == 0 || playerID2 == 0) return false;
+ if (playerID1 > MAX_PLAYERS || playerID2 > MAX_PLAYERS) return false;
```

For neutral units (`playerID == 0`) this is probably correct behavior. But it means genuinely
bad player IDs now fail silently instead of announcing themselves — reduced diagnostic power
in exactly the subsystem currently under investigation.

## 3b. `MScript::Load` divergence

```cpp
- loadStringTable(*inFile);  loadScripts(*inFile);
+ if (inFile) { loadStringTable(*inFile); loadScripts(*inFile); }
```

Retail called these unconditionally. If `inFile` is ever NULL on a path where retail expected
data, scripts silently do not load. Campaign path is unaffected (scripts demonstrably fire),
but the divergence is unexplained.

## 4. Diagnostic footprint — LARGE, needs stripping ⚠️

**~35 diagnostic sites across 25 files**, including library code (`TextureLibrary.cpp`,
`MeshInstance.cpp`, `Direct3D_pipe.cpp`, `Python.cpp`).

Several sit in **per-frame hot paths** and use open-write-close per call. One session produced:

| Log | Size |
|---|---|
| `tmanager_diag.txt` | 4.5 MB |
| `drawagent_init_diag.txt` | 3.0 MB |
| `texlib_diag.txt` | 2.2 MB |
| `toolbar_diag.txt` | 1.5 MB |

**This is not merely untidy — it is a confound.** Synchronous file I/O in render and update
paths materially changes timing and allocation patterns. The open bug is a *deferred* access
violation, i.e. timing- and memory-layout-sensitive. The instrumentation could be shaping the
very behavior being investigated.

Diagnostics whose question is already answered and which should go now:
- `orient_diag` (SpaceShip.cpp ×3) — yaw confirmed 0 in binary; question closed
- `move_diag` (ObjMove.cpp ×2, SpaceShip.cpp) — pathfinding confirmed working
- `TPTLOG` (MScript.cpp, uncommitted) — both teleports confirmed completing
- `mesh_diag` (5 files incl. MeshInstance.cpp) — ship rendering fixed
